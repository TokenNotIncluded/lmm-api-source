# 修复可复现的缺陷

把报告改写成一个能判断对错的例子。记下版本、用户操作、角色、输入、实际结果和预期。用户报告“翻到第二页变成零条”时，保留第二页响应尚未返回的时间段；直接提供已加载的第二页数据会错过故障。

1. 从真实入口向下读到第一个错误决定。核对响应字段、客户端状态和展示条件。数据库问题继续核对查询、排序和事务。用合成账号或隔离夹具保留失败；过滤日志中的凭据和用户数据。
2. 把修复放到拥有该决定的组件。待加载、已确认空结果、请求失败分别保留各自状态。修复测试工具时优先保留真实子进程的退出码、输出格式和跳过数量。
3. 选择现有 runner 中最靠近故障、能稳定变红的用例。冻结输入，在原版本观察失败，再把相同用例交给改后版本。涉及异步时控制请求完成的时机，避免固定睡眠。将原因、修复路径和红绿输出放在同一份交付里。
4. 找到共用同一实现的其他调用方，检查本次改动对它们的公开行为。需验证持久化时重新读取资源；需覆盖浏览器与服务通信时，选用[质量指南](../../../docs/quality.md)里的进程或浏览器入口。

使用现有[自动化验证](../create-verification-skill/SKILL.md)保留反例。提交前记录实际运行的范围，标出仍依赖真实数据库、浏览器或外部服务的部分。
