## 2. 实际补齐的后端能力

### 2.1 Hero SMS

原有页面能够发送配置请求，但 Core 缺少对应执行端。本轮补齐私有 UDS 上的 `ready`、`settings`、`save-policy` 和 `test`，并连接 Extensions 与 Web。浏览器的保存请求现在有真实的持久化实现，接口不再停留在前端控件或 Go 转发层。

保存策略使用旧版本号进行比较，金额倍率保留十进制字符串，并通过临时文件、原子替换与同步写入保存。相同时间的编辑不会静默覆盖新版本。管理请求必须带当前 Root 浏览器会话，并重新验证个人账户、当前超级管理员角色和完整导入权限；后台服务凭证不能替代管理员会话。

API 密钥继续由主机私密文件管理。页面负责启用开关、短信／邮箱选项、倍率和连接测试，不提供无后端支持的浏览器密钥替换操作。现有主机密钥已在服务器内完成迁移，没有输出到报告或浏览器响应。

生产核对包括：

- Core 以实际服务身份启动，私有 `ready` 返回 200，并明确声明配置读取、保存和连接测试能力。
- 无服务凭证请求返回 401；仅有服务凭证、没有用户会话的 `settings` 请求仍返回 401。
- 以实际主机身份使用已配置密钥执行一次只读供应商余额连接请求，2026-11-17 19:38:29 UTC 返回 HTTP 200 和有效余额响应；余额及密钥均未写入报告。
- 生产 Root 的导入权限数据已做只读一致性核对；它不等于完成了真实登录浏览器的 HTTP 保存测试。

**购买能力仍未开放。** Core 返回 `purchases_available=false`，Web 根据账户和会话绑定的能力结果隐藏购买入口，直达页面也不会启动购买查询或资金写入。此次供应商连接成功不代表购号、收短信、临时邮箱购买、退款或资金结算已完成。

### 2.2 签到设置

本轮新增真实的 Root `GET/PUT /api/option/checkin`。它使用签到专用数据库保存策略版本和生效指针，与旧 `/api/option/` 的只读状态分开。金额用十进制整数字符串传递，避免 JavaScript 浮点数造成精度丢失；保存要求旧版本与稳定操作键，处理版本冲突、同请求恢复和未知写入结果。

生产新建独立 `lmm_checkins_prod`，由已验证的 Extensions 二进制执行正式 `install-db` 和 `publish-checkin-policy`，不是直接向策略表插入伪造管理员记录。首次活动策略为 revision 1：

| 字段 | 值 |
| --- | --- |
| 启用 | `true` |
| 基础额度最小值／最大值 | `"1"`／`"500000"` |
| 奖励倍率 | 全部统一为 `1` |
| 日历偏移 | `28800` 秒 |
| 每美元积分单位 | `500000` |
| 初次发布操作键 | `settings-closure-initial-policy-v1` |
| 历史 seed | 空串，表示本轮未进行历史 seed 导入 |

旧配置中的四个白名单值先保存为原始快照，再计算来源摘要。该摘要描述原始配置；生效策略按本轮要求统一倍率，没有把历史快照伪装成已经统一过的输入。

运行账户只能读取策略表并执行一个范围受限的保存函数，不能直接改写策略表、创建数据库对象、切换成 owner，或连接其他受保护业务库。函数固定 `search_path`，PUBLIC 执行权已撤销。临时安装账户已禁用登录，移除 owner 成员关系和数据库连接权，其一次性连接文件已删除。

**配置可保存与奖励可发放是两项能力。** 保存只是持久化奖励范围；真正发放仍由 Core 的资金授权和领取合同决定。本轮没有启用 Core `checkin_rewards`，没有增加账本权限，没有执行真实领取。生产回查 `intentions=0`、`claim_commands=0`。现网 UI 应如实显示资金能力不可用，而不是因为配置保存成功就承诺可以领取。

实现和运维说明：[签到在线设置](https://github.com/TokenNotIncluded/lmm-api-source/blob/561faf51a74a4000ebb2c7d812da4230eba3a213/docs/checkin-settings.md)。

### 2.3 站点入口分流

服务进程就绪还不足以证明网页能够调用它。现网 native 站的通用 `/api` 默认指向 Core，而这些新增设置接口由 Extensions 实现。本轮补齐以下四条精确映射，复用原有 Extensions 上游与访问控制：

| 方法 | 路径 | 实际处理服务 |
| --- | --- | --- |
| GET、PUT | `/api/option/checkin` | Extensions |
| GET、PUT | `/api/option/hero-sms` | Extensions |
| POST | `/api/option/hero-sms/test` | Extensions |
| GET | `/api/hero-sms/capabilities` | Extensions |

`nginx -t` 和 reload 成功。独立核验对三条 GET 和一条匿名 POST 逐一发送真实 HTTPS 请求，并对应检查新产生的访问日志：全部到达 `127.0.0.1:8081`，返回 401 `STORE_LOGIN_REQUIRED`。这个结果证明实际分流和登录门禁生效，不代表已使用生产 Root 会话完成配置写入。

站点访问白名单保持原有策略。标准组件包和现有自动部署流程不重写这份独立站点路由配置，现场映射已纳入本轮部署记录。

## 5. 部署过程与恢复记录

部署前已核对现网版本、配置摘要和数据库合同，并在开发机完整保存旧 Core、Extensions、Web 槽及部署收据。候选包逐一验证归档、源码版本和文件摘要。

Core 在实际服务用户及补充组下执行只读 `check-db` 成功后切换，随后核对健康、实际运行文件和 Hero 私有接口。Extensions 与 Core 分开切换，以便独立恢复。

Extensions 第一次切换后，服务健康已通过，但部署检查脚本使用了不存在的 `/api/announcements`，把 404 文本当成 JSON 解析，触发自动回滚。原链接和配置被恢复；即时健康检查碰到启动竞态，随后独立确认旧进程、原二进制摘要、配置摘要和 HTTP 200 全部恢复。检查了该窗口日志，没有应用 error、panic 或 fatal。纠正检查路径并保留首次失败证据后，第二次切换成功。

真正的强制公告读取路径是 Core 的 `/api/user/self/announcements`。本轮现网匿名请求返回 401 `AUTH_UNAUTHORIZED`；这与实际登录账户此前出现的服务端故障不是同一个验证场景。

Web 第一次切换在 20:57:46 UTC 已取得正确的新首页、6 个带哈希的首屏资源与 WebMCP 文件，但旧入口脚本检查失败，检查程序立即恢复旧 Web 链接并确认旧首页摘要正确，两个后端保持不变。随后定位到实际 HTTPS 的 /static 路径由 native 站变量指向的 Nginx alias 直接读取，没有经过内部 18090 端口；仅给内部端口增加 fallback 并不足以保护 native 站的旧页面。

最终仅为 native 站增加文件选择规则：活动 Web 文件存在时继续读取活动目录，文件不存在时从独立保留目录读取。共享静态模板、公开旧站路由和操作员访问控制均保持原状。一次过早的 reload 后检查仍命中旧 worker 并恢复配置；加入有界的只读等待后，实际观察到 404→200 收敛，随后旧活动资源 200、新保留资源 200、缺失资源 404 都通过。原失败与回退收据保留。

最终在 **2026-11-17 21:01:47 UTC** 原子切换到 web-b，全部发布检查通过；**21:03:00 UTC** 完成独立只读复核。独立复核直接访问 native HTTPS 域名，验证首页、HTML 引用的全部 **7 个同源 JS/CSS**（包含 /extore-callback.js）、610 项实盘文件清单，以及确实不在新清单中的旧入口、独有延迟加载脚本和旧 CSS；后端 PID 和运行文件摘要均保持切换前值。首页与非哈希回调脚本的实际缓存头为 no-cache, must-revalidate；带哈希静态资源沿用原有 public, max-age=31536000, immutable，缺失静态文件的 404 响应也沿用该头，本轮没有改变共享缓存策略。

旧 573 个静态文件与新版本 568 个静态文件按各自清单独立核对并保留，重名文件要求摘要相同，未把旧文件混入新 Web 标准清单。后续部署仍需在清理旧版本前维护这个保留目录；活动目录优先的选择规则不要求未来版本先改写 Nginx 配置。21:05:22 UTC 清理了 3 个已验证的上传归档，共 53,475,889 字节。服务器按 A/B 结构保留一套旧 Core、Extensions 和 Web 槽用于快速恢复，开发机另有完整、重新核对摘要的恢复归档；私密回执与配置备份保留。

3. **Hero SMS 购买尚未实现。** 已上线的是设置与只读连接链路，购买能力明确关闭，没有进行付费购号或邮箱购买。
4. **签到资金、领取验证与历史导入未启用。** 现网可以承载配置管理，但不能据此宣布奖励可领取。本轮没有升级 Core schema、导入历史 seed 或发放任何奖励。
5. **自动注册／邀请奖励与其他仍需主机配置的能力未补成在线管理。** 页面提供真实现有入口和明确状态，未把缺少服务端消费者的字段重新解锁。
6. **支付实际交易不在本轮验证结论中。** Pancake 设置流程包含在最终 Web 中，但没有用真实支付、商户资金或退款来验证本轮发布。
7. **公开域名尚未切换到新架构。** 当前真实发布与验收面向 native 站；旧站服务继续运行。

因此，本轮可准确描述为“设置后端补齐并在新架构站完成部署与分层验证”，不能描述为“全站所有功能全部修好”。
