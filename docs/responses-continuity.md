# Responses 连续性：存储与恢复合同

Core 的连续性映射只保存上游上下文引用和不可变绑定，不保存响应正文。
实现见 [schema](../services/core/schema/responses_continuity.sql)；浏览器 WebSocket
认证与代理配置见[边缘切换合同](edge-cutover-compatibility.md)。

## 保留期限

当前本地映射的保留期限为无限期：没有自动到期、删除或截断入口。
`created_at` 是记录时间，不是清理依据。`active` 表示已经满足激活条件，
不是可删除标志；未激活记录也不能因年代久远而丢弃。

映射引用请求、终态检查点及可能的父映射。财务账本、请求结算、检查点和升级回执
分别遵守自身的不可变证据合同；上游上下文失效或本地凭据撤销不缩短这些证据的
保留期限。运行角色只有受限函数权限，不能直接删除映射或改写绑定。

本地保留不保证上游上下文永久有效。后续请求仍须通过当前身份、权限、路由绑定
和供应商策略校验，上游也可能拒绝已失效的上下文。

若要引入有限期映射，应通过独立 schema 升级明确拆分可过期的解析数据与审计证据，
同时定义父链引用、未完成恢复、幂等重放及备份恢复规则。不得直接添加按
`created_at` 删除记录的定时任务，也不得以手工绕过不可变约束作为归档流程。

## 恢复成本与容量

激活恢复按 `request_id` 游标扫描未激活、已结算的请求。每页返回已经扫描的请求
及各自激活结果；无法激活的记录也必须推进游标。后台结算恢复与激活恢复分别
保存游标，不能用成功激活数量判断是否扫描完毕。

`responses_continuations_inactive` 是按 `request_id` 排序的 `WHERE NOT active`
部分索引，用于排除已激活历史。它仍包含未激活积压，不能代替积压监控或保留策略。

恢复性能验收应覆盖大量已激活历史、少量待激活记录、不可激活前缀及空尾页。
比较索引方案时须记录 `EXPLAIN (ANALYZE, BUFFERS)`、完整一轮的游标推进和结果集，
不能只报告第一页时间，也不能把 SQL 扫描测试当成完整 Rust 结算恢复验收。

扫描索引不能限制磁盘增长。部署容量须计入持续保留的映射、请求、检查点、账本、
索引、WAL 与备份；容量告警不能以删除待恢复记录或财务证据来消除。
